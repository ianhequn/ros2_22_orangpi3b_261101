# 测试与使用指南

面向第一次上手的人，按顺序做完即可。配套：`设计说明.md`（为什么这么设计）、`TODO.md`（开发进度）。

本文档针对 **orangepi 3b 本机 + 真机底盘**（`/dev/tty_chassis`）。仿真侧（WSL2 + Gazebo 串口桥）已在
`ChassisNav_02_u22_wsl` 验证通过，此处不重复。

> 全程把车**架空**（轮子离地），手边留断电开关。第 3、6 级会让电机真转。

## 0. 环境准备

```bash
sudo apt install ros-humble-ros2-control ros-humble-ros2-controllers \
                 ros-humble-xacro ros-humble-robot-state-publisher python3-serial
sudo usermod -aG dialout $USER      # 串口权限，重新登录生效

cd ~/MyWork/Robot/ros2/ws_orangepi_01
colcon build --symlink-install --packages-select dd_chassis_001_driver
source install/setup.bash
colcon test --packages-select dd_chassis_001_driver && colcon test-result --verbose
```
测试全绿（应为 `66 tests, 0 failures`）说明代码本身没问题，可以上实机。

### 0.1 确认 `/dev/tty_chassis` 指向底板而非雷达

本机 udev 规则 `/etc/udev/rules.d/99-usb-serial.rules` 按 USB 物理口固定名字：

| 物理口 | 符号链接 |
| --- | --- |
| `3-1` | **`tty_chassis`**（底板） |
| `4-1` | `tty_lidar`（雷达） |

```bash
ls -l /dev/tty_chassis /dev/tty_lidar          # 应分别指向不同的 ttyUSBx
udevadm info -q property -n /dev/tty_chassis | grep -E 'ID_PATH|DEVPATH'   # 确认是 3-1 那个口
```

⚠️ 该规则文件里的注释把 3-1 / 4-1 写反了（注释说 3-1 是 lidar），**以规则本身为准**。
两个 USB 口插反或符号链接不存在，表现为「收不到任何帧」，先查这里。

## 1. 确认参数

编辑 `config/dd_chassis_001.ros2_control.xacro`，**至少确认这四项**：

| 参数 | 说明 | 怎么得到 |
| --- | --- | --- |
| `serial_device` | 底盘串口，本机固定 `/dev/tty_chassis` | 见 0.1；不要写 `/dev/ttyUSB1`（USB 枚举顺序不稳） |
| `baud_rate` | 波特率 | 固件设置（当前 1000000） |
| `frame_end` | 帧尾魔数 | 固件里 64 字节帧的最后 4 字节，如 `0x7F800000` |
| `imu_yaw_field` | 用 imu1/2/3 哪路做 yaw | 1/2/3 试，看转车体时哪个跟得上 |

其余（`speed_scale`、`invert`、限幅、超时）可以先用默认值，第 3 步标定后再改。

还要确认轮子/电机映射与实物一致（当前 xacro 是 `left→motor 1`、`right→motor 0`，
以第 5 级「手转轮子」的实测为准）：

```bash
grep 'motor_index\|speed_scale\|invert' config/dd_chassis_001.ros2_control.xacro
```

`debug_log` 建议第一次设成 `true`，方便看数据。

> 起 ros2_control 前**必须独占串口**：先关掉 `serial_monitor.py`、串口助手、上位机等任何占用
> `/dev/tty_chassis` 的程序，否则报 `打开串口失败 ... Device or resource busy`。
> 查占用：`sudo fuser -v /dev/tty_chassis`。

## 2. 第 0 级：裸串口自检（不需要 ros2_control）

```bash
ros2 run dd_chassis_001_driver serial_monitor.py \
    --device /dev/tty_chassis --baud 1000000 --frame-end 0x7F800000
```

**期望**：每 0.5 秒一行，帧率 ≈120Hz：
```
帧率≈120.0Hz  imu1=  -1.234 imu2=   0.567 imu3=  89.012  speed0=   0.000 speed1=   0.000  err0=  0.000 out0=   0.000 ...
```

| 现象 | 原因 |
| --- | --- |
| 一直 `... 收不到有效帧` | `frame_end` 值不对 / 波特率不匹配 / 设备选错（回 0.1 确认 tty_chassis 是底板）/ 固件没上电 |
| `打开串口失败 ... Permission denied` | 不在 `dialout` 组（`groups` 查，重新登录生效） |
| `打开串口失败 ... Device or resource busy` | 别的进程占串口（`sudo fuser -v /dev/tty_chassis`） |
| 帧率远低于 120Hz | 波特率偏低（120Hz×64B≈62kbps，至少 115200） |
| 手转轮子 `speed0/1` 不变 | 电机序号或字段含义与预期不同 |

**顺手验证命令能否被接受**（此步独占串口，必须先停掉 ros2_control）：
```bash
ros2 run dd_chassis_001_driver serial_monitor.py --send "SZ qeiM 0 T 100"
```
轮子转 → 格式正确。不转 → 检查前缀是否大写 `SZ`、是否带 `\n`。

## 3. 标定 `speed_scale` 与方向

**a) 测实际转速**：让固件以固定目标值稳定运行后，让轮子转 N 圈并计时 t 秒：
```
实际角速度(rad/s) = 2πN / t
```

**b) 反算系数**：
```bash
ros2 run dd_chassis_001_driver serial_monitor.py \
    --device /dev/tty_chassis --baud 1000000 --frame-end 0x7F800000 \
    --calibrate-motor 0 --target 10 --measured-rad-s 12.5
```
输出：
```
固件目标=10.0 上报 speed 平均值=1250.0000
建议 speed_scale = measured_rad_s / speed_avg = 0.010000
```
把这个值填进 xacro 的 `left_speed_scale`；电机 1 用 `--calibrate-motor 1` 同法填 `right_speed_scale`。

> 换算定义：`关节角速度(rad/s) = 固件 speed 值 × speed_scale`，
> 下发时取倒数：`固件值 = 关节角速度 ÷ speed_scale`。

**c) 方向**：如果发前进指令时某个轮子反转，把对应 `left_invert` / `right_invert` 改成 `true`。
**`speed_scale` 恒为正**，方向只用 `invert` 表达。

## 4. 第 1 级：硬件组件能否加载

```bash
ros2 launch dd_chassis_001_driver chassis_test.launch.py
```

**期望日志**（顺序，设备应为 `/dev/tty_chassis`）：
```

串口已打开并启动 IO 线程: /dev/tty_chassis
IMU 发布已启动: topic=imu frame=imu_link rate<=120.0Hz

```

另开终端：
```bash
ros2 control list_hardware_components     # state: active
ros2 control list_hardware_interfaces     # 4 个 state + 2 个 command，command 显示 [claimed]
```

| 现象 | 原因 |
| --- | --- |
| `参数缺失: 缺少必填参数 "frame_end"` | xacro 没填 |
| `参数非法: 参数 "baud_rate" 值非法` | 填了非数字 |

| `打开串口失败 ... Permission denied` | 没加 dialout 组 |
| `打开串口失败 ... Device or resource busy` | 别的进程占着（如 serial_monitor，`sudo fuser -v` 查） |
| `打开串口失败 ... No such file` | udev 符号链接没生成，回 0.1 |

## 5. 第 2 级：数据流出是否正确

`chassis_test.launch.py` 默认会启动打表（不想看加 `monitor:=false`）；
用 `chassis_hw.launch.py` 时默认不启动打表，需加 `monitor:=true`：
```
关节速度[rad/s] wheel_l= +0.000 wheel_r= +0.000 | yaw=+175.87° yaw_rate=+0.000 | odom vx=+0.000 wz=+0.000
```

1. **轮速**：手转左轮 → `wheel_l` 变化、`wheel_r` 不动。
   若相反，说明 `wheel_l/wheel_r` 或 `left/right_motor_index` 与实物不符（当前 xacro 是 left=motor1, right=motor0）。
2. **方向**：向前推车 → 两轮都应为**正**。（反了就改 `invert`）
3. **yaw**：车体俯视逆时针转 → yaw 应**增大**（0°→+90°）。
   - 相反：`imu_yaw_sign` 改 `-1`
   - 不跟随：`imu_yaw_field` 换 1/2/3
   - 转 90° 显示 1.57：`imu_angle_is_deg` 应为 `true`
4. **频率**：
```bash
ros2 topic hz /joint_states     # ≈ 60（本包 controllers.yaml 的 update_rate）
ros2 topic hz /imu              # ≈ imu_publish_rate（120）
ros2 topic echo /imu --once     # orientation.z/w 非 0；angular_velocity_covariance[8]=0.01
```

## 6. 第 3 级：指令闭环

### 6.1 无交互测试（先跑这个确认通路）

```bash
# 方式 A：话题直接发（必须 BEST_EFFORT，否则消息被静默丢弃！）
ros2 topic pub -r 10 --qos-reliability best_effort \
  /diff_drive_controller/cmd_vel_unstamped \
  geometry_msgs/msg/Twist '{linear: {x: 0.05}}'

# 方式 B：用打表工具顺带发（内部已用 BEST_EFFORT）
ros2 run dd_chassis_001_driver chassis_monitor.py --cmd-vx 0.05    # 慢速直行
ros2 run dd_chassis_001_driver chassis_monitor.py --cmd-wz 0.3     # 原地左转
```

### 6.2 键盘遥控（官方 teleop_twist_keyboard）

安装（已装可跳过）：
```bash
sudo apt install ros-humble-teleop-twist-keyboard
```

⚠️ **官方包必须经 QoS 中继，否则按键完全无反应且无报错**。
原因：humble 版 `teleop_twist_keyboard` 2.4.1 **没有 `qos` 参数**，发布端固定用默认
`RELIABLE`；而 `diff_drive_controller` 的订阅固定 `BEST_EFFORT`。DDS 规定
**RELIABLE 发布者无法向 BEST_EFFORT 订阅者投递**（反方向可以）——消息直接被丢。
所以网上常见的 `-p qos_reliability:=best_effort` 在本版本上会报「参数不存在」。

**开三个终端**（先跑第 4 级的 launch）：

```bash
# 终端 1：硬件接口
ros2 launch dd_chassis_001_driver chassis_test.launch.py

# 终端 2：QoS 中继（本包自带）
ros2 run dd_chassis_001_driver qos_relay.py \
  --in /cmd_vel --out /diff_drive_controller/cmd_vel_unstamped

# 终端 3：键盘遥控（发布到默认 /cmd_vel 即可，中继会转）
ros2 run teleop_twist_keyboard teleop_twist_keyboard
```

按键（US 键盘布局）：

| 键 | 作用 |
| --- | --- |
| `i` / `,` | 前进 / 后退 |
| `j` / `l` | 左转 / 右转 |
| `k` | 停 |
| `u` `o` `m` `.` | 斜向走 |
| `q`/`z` | 整体速度 ±10% |
| `w`/`x` | 仅线速度 ±10% |
| `e`/`c` | 仅角速度 ±10% |
| `Ctrl-C` | 退出 |

默认速度 `speed=0.5 m/s`、`turn=1.0 rad/s` 对本底盘偏快（`max_velocity` 限幅 0.5），
建议先用小值：
```bash
ros2 run teleop_twist_keyboard teleop_twist_keyboard \
  --ros-args -p speed:=0.1 -p turn:=0.3
```

> 启动后在终端 3 里按键才有输出（它不循环发，只按键时发一次）。
> ⚠️ **松键不会停车**：teleop 只在你按键时发一条 Twist，之后就什么都不发；
> 而 `cmd_vel_timeout`（0.5s）会在超时后自动归零，所以实际效果是**松键后 0.5s 停**。
> 但不要依赖它作安全手段，停就按 `k`，下车前先 `Ctrl-C`。

### 6.3 检查表

| 项目 | 期望 |
| --- | --- |
| 直行 | 两轮同向正转，车走直线，`odom vx ≈ 0.05` |
| 左转 | 左轮反转、右轮正转，车逆时针 |
| 停车 | 停发 cmd_vel 超过 `cmd_vel_timeout`（0.5s）→ 两轮归零 |
| 里程 | 直线走 1m，`odom` 的 x 变化 ≈1m（差得多回第 3 步重标） |

**QoS 是大坑**：`diff_drive_controller` 的订阅是 `BEST_EFFORT`，nav2 / `teleop_twist_keyboard`
默认用 `RELIABLE` 发布 → 消息被丢，且**无任何报错**。诊断：
```bash
ros2 topic info /diff_drive_controller/cmd_vel_unstamped -v   # 看两端 Reliability 是否一致
ros2 topic hz /diff_drive_controller/cmd_vel_unstamped        # 中继正常时按键就应有流量
```
键盘无反应时依次查：终端 2 有没有「已转发 N 条」？`ros2 topic info -v` 两端是否一致？

## 8. 接导航（真机联调）

1. 把 `config/dd_chassis_001.ros2_control.xacro` 的 `<ros2_control>` 块替换掉机器人 URDF 里
   仿真用的 `ign_ros2_control` 块。

   `/diff_drive_controller/cmd_vel_unstamped`，**且 relay 的发布端必须是 BEST_EFFORT**。

## 9. 参数速查

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `serial_device` | /dev/tty_chassis | 串口设备（udev 固定名） |
| `baud_rate` | 1000000 | 波特率 |
| `frame_end` | 0x7F800000 | 帧尾魔数（必填） |
| `frame_timeout_ms` | 500 | 断线判定，建议 ≥5 个上报周期 |
| `timeout_stops_motors` | true | 断线时是否下发 0 |
| `max_wheel_velocity` | 25.0 | 角速度限幅 rad/s，≤0 不限 |
| `command_epsilon` | 0.01 | 下发去重阈值 rad/s |
| `command_repeat_period_ms` | 0 | >0 周期重发（固件要心跳时） |
| `left/right_wheel_joint` | wheel_l/wheel_r | 必须与 URDF 一致 |
| `left/right_motor_index` | 1 / 0 | 固件电机号，必须不同（以实测映射为准） |
| `left/right_speed_scale` | 0.030063 | 换算系数，必须 >0（标定后填） |
| `left/right_invert` | false | 方向取反 |
| `publish_imu` | true | 是否发 /imu |
| `imu_topic` | imu | 话题名 |
| `imu_frame_id` | imu_link | 必须能在 TF 树中找到 |
| `imu_yaw_field` | 3 | 1~3 |
| `imu_angle_is_deg` | true | 固件角度单位 |
| `imu_yaw_sign` | 1.0 | 1 或 -1 |
| `imu_publish_rate` | 120.0 | 发布频率上限（抽帧） |
| `imu_stamp_offset_calib_s` | 10.0 | 时间偏移校正周期 |
| `debug_log` | false | 打印帧与下发内容，上线前关 |

## 10. 常用工具

```bash
# 裸串口监视（不启动 ros2_control）
ros2 run dd_chassis_001_driver serial_monitor.py --device /dev/tty_chassis --frame-end 0x7F800000

# 手动发一条固件命令（需先停掉 ros2_control / 其他占串口进程）
ros2 run dd_chassis_001_driver serial_monitor.py --send "SZ qeiM 0 T 100"

# 标定
ros2 run dd_chassis_001_driver serial_monitor.py --calibrate-motor 0 --target 10 --measured-rad-s 12.5

# 打表（可顺带发指令）
ros2 run dd_chassis_001_driver chassis_monitor.py [--cmd-vx 0.05 | --cmd-wz 0.3]

# QoS 中继：RELIABLE 发布端 -> BEST_EFFORT 订阅端（键盘遥控必备）
ros2 run dd_chassis_001_driver qos_relay.py --in /cmd_vel --out /diff_drive_controller/cmd_vel_unstamped

# 键盘遥控（见 6.2，需配合上面的中继）
ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -p speed:=0.1 -p turn:=0.3

# 启动验证（自带 robot_state_publisher + 打表）
ros2 launch dd_chassis_001_driver chassis_test.launch.py [monitor:=false]

# 只起硬件接口，不发 TF（与 WSL2 导航侧 robot.launch.py 联调时用）
ros2 launch dd_chassis_001_driver chassis_hw.launch.py [monitor:=true]
```

两个 launch 都加载 `config/controllers.yaml`，都是 `enable_odom_tf: false`
（odom→base_footprint 交给 EKF）。区别只在是否启动 `robot_state_publisher`；
两边各发一份 TF 会让 `base_footprint→base_link` 出现两个值，雷达高度算错。

## 11. 排障顺序（出问题是这个顺序，别跳）

0. **设备层**：`ls -l /dev/tty_chassis` 存不存在、指向底板还是雷达（0.1）？有没有进程占串口？
1. **串口层**：`serial_monitor.py` 能不能收到 120Hz 帧？
2. **参数层**：`ros2 control list_hardware_components` 是不是 `active`？
3. **数据层**：`/joint_states` 频率对不对、手转轮子数值动不动？
4. **指令层**：`ros2 topic info <cmd topic> -v` 两端 QoS 是否一致？`debug_log` 有没有打出 `SZ qeiM`？
5. **数值层**：动但很慢/不转 → 回第 3 步查 `speed_scale`。
